# QQ 空间动态与相册集成归档方案

调研日期：2026-10-24。以下项目能力依据项目自身说明，不代表已使用真实账号验证。

后续进展：用户已选择桌面软件形式，当前已实现 PySide6 桌面预览版及共享同步服务。下文“当前原型核查”保留调研时的基线情况；最新实现与验证边界见 [桌面版验证记录](desktop-validation.md)。

## 需求边界

暂将“QQ 动态”解释为 QQ 空间的说说及其配图，不包含 QQ 聊天记录。首版以本人空间为默认来源，同时导出说说文本、发布时间、位置、配图，以及相册结构、照片、照片说明和可获得的时间信息。

建议面向普通用户提供桌面界面，沿用当前 Python 归档核心。最终界面形式待用户选择；浏览器扩展也是可选方向，尚未锁定桌面技术栈。

## 建议的首版操作流程

1. 打开工具，选择备份文件夹。
2. 在官方 QQ 登录流程中扫码，显示当前登录账号。
3. 勾选“说说及配图”“相册照片”，支持单独选择相册；后续加入时间范围。
4. 先读取清单，再显示条目数与下载任务进度；读取完成和下载完成分别显示。
5. 导出后显示成功、失败、未下载、无权限、画质降级情况，可重试失败任务。
6. 打开本地存档，按说说、相册、时间浏览，并搜索正文和说明。

登录失效时保留已归档内容，提示重新登录；重新执行应避免重复条目。媒体失败不能被写成“全部完成”。不要求用户合并两个工具生成的文件夹。

## 数据与架构

保留已有分层：登录会话 → HTTP 客户端 → 说说/相册采集器 → SQLite → 媒体下载 → 离线导出。将同步编排从 CLI 中提取为公共服务后，再接桌面界面，使 CLI 和界面共享同一套行为。

- 说说使用账号和 tid 标识；相册使用账号和 album_id；照片保留其来源相册与服务端标识。
- 文本、原始响应、媒体地址、实际本地路径分别记录；媒体共用文件时仍保留各自的来源关系。
- 拍摄时间、上传时间、说说发布时间保持独立；缺少拍摄时间时显示回退来源。
- 下载记录应包含任务状态、尝试次数、错误类型、实际文件大小和画质来源。
- “重新运行跳过完整文件”与“从文件中间续传字节”是不同能力，界面与说明应明确区分。
- 图片地址可能是 QQ 媒体 CDN，不应宣称全部网络请求只到 qzone.qq.com；登录凭据只能发往所需的可信登录/接口域。

## 当前原型核查

当前目录已有 Python 0.1.0 原型，具备扫码/Cookie 登录代码、说说与相册采集、SQLite、媒体下载、离线 HTML 查看器和命令行入口。

本轮原有 13 项测试与 Ruff 检查通过。测试主要覆盖部分解析、字段规整、存储及导出，未执行真实账号登录和数据备份，不能据此承诺当前私有接口可用或导出完整。

代码中需要优先核实的地方：

1. 相册分页依赖 nextPageStart 和 albumsInUser；缺失或不前进的游标可能造成提前结束或重复请求，需要补异常响应测试。
2. 原图只选择一个地址，当前下载失败不会自动切换到 origin/normal；“改 URL 后自然回退”的注释与行为不一致。
3. 媒体下载已有即时重试，但没有持久失败队列；同步游标表存在，采集流程尚未接入游标恢复。
4. 当前跳过完整文件属于文件级恢复，不是 HTTP Range 字节续传。
5. 离线相册会过滤没有本地照片的相册，容易掩盖未下载或空相册状态。
6. 说说已有点赞/评论数量与原始响应存储，但没有完整评论、回复的独立分页归档。
7. 视频源解析与播放尚不完整；不能把视频封面下载成功算作视频备份成功。
8. 本地 export/status/verify 依赖会话中的账号，未来应改为从存档选择账号，以便退出登录后仍能管理备份。

## 实施顺序与验收

第一步：加固当前核心。修复分页终止条件与原图回退，持久记录失败任务，区分中断、部分成功和全部完成；测试覆盖多页、会话过期、下载失败、重复运行与异常字段。

第二步：实现选定的界面。共享同步服务，通过后台任务和进度事件驱动界面，支持选择内容、取消、重试与打开目录。使用明确标注的演示数据核查布局，再单独做真实账号联调。

第三步：完善归档。保留空相册及未下载条目，新增清晰的备份报告、可迁移的 JSON、断网浏览验证；媒体完整性检查应包括说说配图。

第四步：在基础流程可靠后扩展视频、完整评论、Markdown/CSV 和跨来源媒体去重。

真实验收至少需要：一个包含多页说说与多个相册的本人账号；核对界面可见条目、存储条目、实际下载文件数；人为中断后重试；登出后离线打开；验证无原图、失效媒体、空相册与失败提示。扫码确认由用户在手机上完成，开发过程不要求用户在聊天中发送 Cookie。
